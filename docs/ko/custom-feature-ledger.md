# PocketRisu 개조 기능 장부

이 문서는 공식 PocketRisu 업데이트를 받을 때 개조 기능의 소유 파일, 도입 이유, 검증 상태와 상류 중복 여부를 빠르게 판단하기 위한 유지보수 장부입니다.

## 기준

- 상류 기준: 공식 PocketRisu v1.12.0
- 개조 브랜치: `feature/external-assets`
- 최신 검증 배포 커밋: `e46daadda`
- 외부 프로젝트 전체 병합: 없음
- HaejeokRisu `b6651`의 GPL v3 코드·구조 중 사이드바 지연 로더와 제한형 이미지 캐시 원칙을 PocketRisu API에 맞춰 이식했습니다. 상세 내용은 `docs/ko/haejeok-adoption.md`에 기록합니다.
- PocketRisu Kei `kei-v2.1.1`에서 검토한 안정 ID 기반 사이드바 드래그 원칙을 현재 UI 구조에 맞춰 이식했습니다. 후속 후보와 제외 범위는 `docs/ko/kei-adoption.md`에 기록합니다.

Chromium의 기본 스크롤 앵커링은 DOM 순서로 앵커를 고르는데, 최신 메시지가 앞에 오는 목록에서는 화면 맨 아래 메시지가 앵커가 되어, 위쪽 메시지에서 버튼으로 패널이 열리면 그 높이만큼 화면을 밀었습니다(버튼 361px→61px). 보던 자리는 이 기능의 리더 앵커가 지키고, 앵커링이 없는 Safari는 원래 그렇게 동작했습니다. 보던 자리는 메시지 윗변이 아니라 화면 맨 위에 걸친 그 메시지 안의 요소(문단, 패널; fixed·sticky 제외)를 기준으로 지킵니다. 메시지 윗변 기준일 때는 같은 메시지 안에서 읽는 줄 위의 배너·캐러셀이 커졌다 줄었다 하면, 읽던 줄이 그 높이만큼 위아래로 흔들렸습니다(헤드리스에서 264↔444px). 그 요소가 다시 그려져 없어지면 메시지 윗변 기준으로 돌아갑니다. 또 맨 아래 따라가기(자동 스크롤)는 이 채팅에서 답변을 생성하는 동안에만 하고, 채팅을 연 직후의 따라가기 고정은 3초가 지나면 풉니다. 다 받은 답변 안의 애니메이션이 화면을 끌고 다니지 않게 하기 위해서입니다. 카드의 HTML/CSS 버튼이 본문을 통째로 다시 그려도(`{@html}`이 옛 노드를 버리고 새 노드를 넣음), 읽는 사람이 스크롤해 둔 카드 안 상자(로그·상태창·가로 탭)는 본문 안 같은 자리(또는 같은 id)의 새 상자에 그 위치를 다시 넣습니다(`keepInnerScroll`). 새로 그린 직후 이미지가 덜 불러와져 위치가 잘리면, 사람이 다시 만지기 전 2초 동안은 이미지가 불러와질 때 다시 맞춥니다. |

## 자동 검문

- 기계 판독 계약은 `docs/ko/custom-feature-contract.json`입니다.
- `pnpm run check:custom`은 핵심 기능의 소유 파일, 핵심 심볼, 회귀 테스트 파일과 이 문서의 ID를 검사합니다.
- 이 검사는 기능이 **존재하는지** 잡는 1차 검문입니다. 기능이 올바르게 작동하는지는 계약에 적힌 회귀 테스트와 `pnpm test`, `pnpm check`, `pnpm build`로 확인합니다.
- 상류에 같은 기능이 생겨 개조 코드를 제거할 때에는 상류 대체 파일·테스트를 계약에 먼저 등록합니다. 계약만 삭제하여 검문을 피하지 않습니다.

## 업데이트 충돌 판단 순서

1. 현재 배포 커밋에 `pre-upstream-vX.Y.Z` 태그를 남기고 추적 중인 변경이 없는지 확인합니다.
2. 상류 업데이트는 실사용 브랜치에 바로 덮지 않고 임시 통합 브랜치나 worktree에서 merge합니다.
3. 충돌을 해결한 직후 `pnpm run check:custom`을 실행합니다. 실패한 기능은 복구하거나 상류 대체 구현으로 계약을 갱신합니다.
4. 계약에 등록된 회귀 테스트를 먼저 실행하고, 이어서 `pnpm check`, `pnpm test`, `pnpm build`를 통과시킵니다.
5. 저장 형식·에셋 URI·채팅 동시성처럼 데이터 안전에 영향을 주는 기능을 UI 기능보다 먼저 실데이터 복제본에서 검증합니다.
6. 새 빌드는 기존 정적 조각을 즉시 지우지 않는 방식으로 배포하고 PC·모바일 기본 동작을 확인합니다.
7. 빌드와 실제 C 드라이브 서버 배포까지 끝난 커밋만 이 장부에서 `완료`로 바꾸고 기준 버전을 갱신합니다.

## 2026-09-05 채팅 저장 충돌 회귀 수정

- **확인한 원인:** 본문 POST의 성공 응답 뒤 catalog stub의 name/lastDate/folderId/modules를 병합하면서 전체 바이트 ETag가 바뀌었습니다. 다른 기기가 없어도 다음 본문 저장이 409가 되는 경로를 실제 서버 테스트로 재현했습니다.

## 2026-09-06 프로바이더 플러그인 암호화 호환 수정

- **확인한 원인:** V3 플러그인은 opaque `srcdoc` iframe에서 실행됩니다. Chromium 152 계열에서는 이 프레임의 `crypto.subtle`이 제공되지 않아 provider-manager가 요청 지문을 만들기 위한 `digest`를 읽는 순간 채팅이 중단됐습니다.
- **SHA-256 호환:** 샌드박스가 `crypto.subtle.digest()`를 제공하지 않을 때만 호스트 API로 연결하며, 호스트에서도 네이티브 호출이 거부되면 기존 상수 메모리 SHA-256 구현을 사용합니다. 입력은 복사하여 플러그인이 소유한 버퍼가 RPC 전송 중 분리되지 않게 합니다.
- **서명 키 경계:** provider-manager가 이어서 사용하는 HMAC 및 Vertex AI RSA 서명은 부모 페이지의 키 레지스트리로 가져옵니다. 플러그인에는 불투명한 임시 ID만 돌려주며, WebCrypto가 있으면 `CryptoKey`, 없으면 제한된 HMAC 키 바이트 또는 파싱된 RSA 지수만 해당 플러그인 인스턴스 메모리에 둡니다. 비밀 키를 PocketRisu 서버로 전송하거나 저장하지 않습니다.
- **평문 LAN 대체:** 휴대폰에서 `http://192.168.x.x`로 접속해 부모 페이지 자체가 비보안 컨텍스트여도 상수 메모리 SHA-256, HMAC-SHA-256 및 PKCS#1 v1.5 RS256 계산으로 서명을 마칩니다. 다른 알고리즘은 조용히 흉내 내지 않고 거부합니다.
- **검증 범위:** SHA-256 표준 벡터, 네이티브 우선 사용, Node HMAC 결과 일치, 임시 2048비트 PKCS#8 키의 순수 브라우저 서명을 Node 공개키로 검증하는 회귀 테스트를 통과했습니다. 실제 외부 모델 호출은 요금과 채팅 변경을 발생시키므로 자동 검증에서 제외합니다.
